## 1. Where is the LLM client, which provider and models, and how are structured outputs enforced?

### Takeaway
There is one provider (Anthropic) behind one thin, text-in/text-out seam (`LlmClient.complete`) with three implementations (live, replay-from-fixtures, recording). Every model constant is `claude-haiku-4-5` except the English meaning check (`claude-sonnet-5`). Structure is enforced by the API's JSON-schema output mode plus a second zod/allowlist validation in deterministic code at every call site; there is no tool-use for structure, no retry-on-invalid-JSON at the client (retry exists only in the phrasing/translate/insights ladders), and no prompt caching.

### Cited Findings
- The shared seam: `LlmRequest {model, maxTokens, temperature?, system, question, jsonSchema?, thinking?}` and `LlmResponse {outputText, model, stopReason, usage{inputTokens, outputTokens}}`; `LlmClient { complete(request) }`. The response is a plain string (`outputText`); there is no field for token probabilities, logprobs or a typed value. — `src/answer/llm/client.ts:28-59`
- Exactly three implementations: `AnthropicLlmClient` (real), `ReplayLlmClient` (CI, keyed by SHA-256 of the whole request), `RecordingLlmClient`. — `src/answer/llm/client.ts:1-22`, `:96-141`, `:202-270`
- The real client calls `sdk.messages.create` and passes the schema as `output_config.format = {type:'json_schema', schema}`; it throws on `stop_reason === 'refusal'` and on `max_tokens` truncation. It does no retry of its own and no JSON repair. — `src/answer/llm/client.ts:103-126`
- Provider dependency: only `@anthropic-ai/sdk ^0.128.0` in both `package.json:92` and `web/package.json:18`. No OpenAI, AI-SDK, Voyage, Cohere or Gemini dependency exists (grep of both `package.json` files). The repo has no embedding model call and no vector DB: ADR 002 rejects pgvector in Phase 0 and lists "catalog past ~50 tables or intent-matching misses" as the trigger to enable it (`docs/decisions/002-postgres-system-of-record.md:23`, `:38`).
- Request hash covers model, sampling, thinking, system prompt, schema and user text, so any model/prompt/schema change orphans recorded fixtures and the replay client fails loudly. "HASH-STABILITY CONSTRAINT: renaming a field ... would orphan every committed fixture." — `src/answer/llm/client.ts:13-21`, `:209-234`
- Fragility of that hash is a recorded open item: a non-behavioural `zod` bump changed `z.toJSONSchema()` output and broke 49 of 1780 backend tests and the 6/6 refusal gate; proven by pinning zod back. — `docs/open-questions.md:111` (row #200)
- Schema-to-API plumbing: `oneOfToAnyOf` rewrites zod `oneOf` to `anyOf` because the structured-output dialect rejects `oneOf`. — `src/answer/llm/json-schema.ts:10-28`. Structured-output limits (no numeric min/max, all fields required, `additionalProperties:false`) push range checks into deterministic code. — `src/answer/intent/schema.ts:7-10`
- Model constants (all named, one per module): intent `INTENT_MODEL='claude-haiku-4-5'` (`src/answer/intent/client.ts:33`); phrasing `PHRASING_MODEL` (`src/answer/compose/prompt.ts:32`); semantic check (`src/answer/compose/semantic-check.ts:32`); table rerank (`src/catalog/rerank.ts:35`); measure fit (`src/ingestion/onboarding-fit.ts:28`); table parse (`src/answer/table-parse/parse.ts:66`); websearch (`src/websearch/client.ts:35`); dataset instruct (`src/attachments/instruct/parse.ts:35`); dataset copilot (`src/attachments/copilot/parse.ts:18`); CBS chart copilot (`src/chart/copilot/parse.ts:13`); all `'claude-haiku-4-5'`. English meaning check `MEANING_CHECK_MODEL='claude-sonnet-5'` (`src/answer/translate/meaning-check.ts:20`). The English translate call reuses `PHRASING_MODEL` (`src/answer/translate/prompt.ts:10`, `:109`). Insights/headline reuse `PHRASING_MODEL` (`src/chart/insights-phrase.ts:27`, `:147`, `:276`, `:279`).
- Live API reports the pinned snapshot: `claude-haiku-4-5-20251001`, 47 calls in the 2026-09-26 live benchmark. — `benchmark/live-benchmark-report.json` (`usage.byModel`)
- Sampling handling differs by model: Haiku gets `temperature: 0`; Sonnet 5 "rejects non-default sampling params" and needs `thinking:'disabled'`. — `src/answer/llm/client.ts:36-47`; `src/answer/translate/meaning-check.ts:127-133`. The un-adapted param silently API-errored every call in the first Sonnet escalation attempt. — `src/catalog/rerank.ts:24-33`, `:57-63`
- Websearch is a second, separate client on purpose (`AnthropicWebSearchClient`, own interface `WebSearchClient.search(question): Promise<WebSection>`), using Anthropic's native `web_search_20250305` server tool, `max_uses: 3`, 45 s timeout, `max_tokens 16000`, never throws (returns typed `{status:'failed'}`). — `src/websearch/client.ts:1-20`, `:35-62`, `:69-88`
- Post-parse validation pattern (every decision call): zod `strictObject` schema is the single source for both the API JSON schema and the call-site validator; hard allowlists check that returned ids/codes are members of what was sent. Example: rerank `tableId` must be in the shortlist, else `RerankValidationError`. — `src/catalog/rerank-schema.ts:1-8`, `:46-60`; intent `validateRawParse` after each call — `src/answer/intent/parse.ts:59-62`
- Retry-on-invalid exists only where the output is prose: phrasing ladder (LLM, strict retry, then deterministic template) — `src/answer/compose/compose.ts:288-335`; translate ladder up to 2 attempts then Dutch fallback — `src/answer/translate/translate.ts:401-440`; insights one stricter retry then template captions — `src/chart/insights-phrase.ts:266-282`. Decision calls fail safe instead (rerank error -> disclose, `src/catalog/find.ts:46-58`; fit error -> next candidate, `src/ingestion/onboarding-fit.ts:191-199`).
- Prompt caching: none. `grep cache_control` over `src`, `web/app`, `web/lib` returns nothing, and lessons-learned records "The client sends no `cache_control`, so nothing is discounted across a run". — `docs/lessons-learned.md:6234`; ADR 004 defers caching until spend exceeds about EUR 50/month. — `docs/decisions/004-llm-usage.md:20`, `:37`
- Per-answer tracking: `LlmCallTracker.wrap(role, client)` records `{role, model, inputTokens, outputTokens}` per completed call into the audit row's `llm_calls`; roles are `intent|clarify|followup|compose|semantic_check|translate|meaning_check|table_parse`. — `src/answer/audit/track.ts:14-30`, `src/answer/audit/types.ts:19-31`. The audit row stores one whole-answer `latency_ms`, not per-call latency. — `src/answer/audit/write.ts:78`, `:142`, `:177`
- Where clients are constructed at request time: `web/app/actions.ts:603-604` (intent + answer), `:634` (web), `:674`/`:683` (finder rerank), `:1194-1195`; dataset chat `web/app/dataset-actions.ts:426`; dataset copilot `web/app/dataset-copilot-actions.ts:127`; CBS chart copilot `web/app/chart-copilot-actions.ts:77`; insights `web/app/chart-insights-actions.ts:54`; headline `web/app/chart-headline-actions.ts:33`; English `web/lib/english-answers.ts:30-31` (own SDK instance, `maxRetries:0`, 20 s timeout); anonymous trial uses a separate key `web/app/trial-actions.ts:73`; batch: onboarding cron `web/app/api/onboarding-cron/route.ts:80-90`, table-lane job `web/lib/table-lane-job-deps.ts:25-30`.

### Inferences
- A typed-decision model cannot be dropped in behind `LlmClient` as-is, because the seam's response type is only `outputText: string` plus token usage (`client.ts:50-55`). A Jev integration would need either a sibling interface (the websearch precedent, `src/websearch/client.ts:58-60`) or an additive optional field on the response (the client header says new optional request fields are hash-safe, `client.ts:17-19`).
- The schema-first design (zod schema -> JSON schema -> allowlist validation) means the typed output contracts a Jev-style model would have to emit already exist and are code-defined for the decision calls.

### Gaps
- No direct evidence in the repo of how Jev's API would map onto these schemas; that is outside this repo-only task.

## 2. Complete call-site inventory (request-time and batch)

Legend: D = decision (typed output the code consumes), P = prose (text a reader sees or free text stored). "Prompt size" is the prompt source file size in bytes unless a measured token count is given. Flag state is from `docs/RUNBOOK.md` unless noted.

### Takeaway
There are 16 distinct LLM roles. 11 are decision-shaped (typed slot objects, enum/choice picks, booleans), 5 are prose (answer body, English translation, chart insights, headline, web search). The core Dutch answer path is exactly two sequential Haiku calls (one decision, one prose); everything else is conditional or behind a flag. Roughly ten features the brief lists have NO LLM call of their own (chips, meta-question templates, refusal/clarification text, unit expansion, conversation memory, chart-fit, alternate reading).

- Whether `intent-calibration-report.json` `usage` counts 234 calls (78 x 3) is my assumption; the session-129 6.6K/call and this ~10K/call figures differ, plausibly because the registry vocabulary grew, but I did not verify the cause.

## 3. Decision vs prose: share of per-question spend and latency

### Takeaway
By input tokens the decision calls dominate heavily (intent parsing is the single biggest cost, prose phrasing is a small prompt); by output tokens and likely wall-clock the two core calls are the same order of magnitude. No per-stage latency is logged in production, so the latency split is an ESTIMATE. Total LLM cost per Dutch answer is on the order of one cent.

### Cited Findings
- MEASURED whole-run usage, live benchmark 2026-09-26 (20 tasks): 47 Haiku calls, 257,279 input tokens, 3,832 output tokens; gate PASS 14/14 + 6/6 + 0 fabricated; 4 template fallbacks. — `benchmark/live-benchmark-report.json` (`usage`, `gate`, `informational`)
- MEASURED phrasing per call: 17,297 in / 810 out over 14 answer cases (13 LLM-phrased, 1 template) -> ~1.2K in / ~58 out per case (DERIVED). — `benchmark/answer-eval-report.json`

### Inferences (ESTIMATES, labelled)
- Cost per Dutch answered question: intent ~6.6-10K input + ~120 output tokens plus phrasing ~1.2K input + ~58 output. At the repo's ~$1.02/M input that is roughly $0.008-0.012 input-side per question; output at Anthropic Haiku list price (not stated in the repo, my assumption ~$5/M) adds well under $0.001. Cross-check: 257,279 input tokens / 20 tasks ~ 12.9K per task -> ~$0.013 per task at the same price basis (includes clarify/follow-up/retry calls in the mix). Consistent with "well under EUR 0.02".
- Decision vs prose split of INPUT tokens on the core path: decisions roughly 85-90% (intent 6.6-10K vs phrasing 1.2K). Split of OUTPUT tokens: roughly 2:1 decision:prose (121 vs 58 per call, both derived). Because response latency is mostly output-token time plus fixed overhead, the two core calls probably each cost on the order of 1-2 s, i.e. about half the LLM wall-clock is the intent decision and about half is phrasing. This is an inference; it has no per-stage measurement behind it.
- The intent decision call alone is the largest cost and likely the largest single latency item that a fast typed model could target; conditional decision calls (rerank, fit, semantic check, meaning check) add cost only on rarer paths but add serial latency when they fire (English path: up to two translate + two meaning calls inside a 20 s cap, `docs/decisions/059-english-meaning-check.md:57`).
- No prompt caching is used, so a 6.6-10K-token registry-generated system prompt is billed at full input price on every intent call. That is a cost lever independent of any new model.

### Gaps
- No per-stage (intent vs phrasing vs DB) latency measurement exists in committed files; `audit_answers.latency_ms` is whole-answer and `llm_calls` carries tokens but no per-call time (`src/answer/audit/types.ts:19-31`). The raw benchmark audit dump (`benchmark/audit-run-live.json`, referenced by `package.json:36`) is not committed, so I could not compute a split.
- Output-token pricing and Haiku 4.5 list prices are not stated in the repo; my $5/M output figure is external knowledge, not verified here.

## 5. ADR 004 and ADR 012: model choice, fallback, cost tier, swap conditions; invariants; principle (c)

### Takeaway
ADR 004 explicitly calls the provider a swappable default with "a thin adapter", assigns a small/fast model to parsing and a mid-tier to phrasing (later moved to Haiku for cost), and gives an escalation ladder (richer aliases, then embeddings, then a bigger model). Any replacement must preserve R1-R11, R7's confidence-and-clarify behaviour and fail-closed defaults. Principle (c) needs a confidence signal that is honest enough to gate answering; the repo already shows self-reported LLM confidence is imperfect.

### Cited Findings
- ADR 004: LLM in "exactly two places" (later three, with the reject-only checker), both schema-validated; provider Claude API, "The adapter around LLM calls is thin enough that provider choice is swappable; this is a default, not a lock-in"; "small/fast model for intent parsing, a mid-tier model for phrasing". — `docs/decisions/004-llm-usage.md:11-19`, `:41-43`
- ADR 004 alternatives: rejected a self-hosted open-weights model because it "adds serious ops for one non-developer, at lower Dutch-language quality ... revisit only if provider privacy terms become untenable." — `docs/decisions/004-llm-usage.md:27`
- ADR 004 revisit triggers: spend above ~EUR 50/mo -> caching and re-evaluate tiers; intent accuracy below the Phase 0 gate -> "richer registry aliases first, embeddings second, bigger model last"; accounts launch -> GDPR/DPA. — `docs/decisions/004-llm-usage.md:35-39`
- GDPR seam: user questions flow to the provider, DPA and retention decision required from Phase 1; 2-year retention decided. — `docs/decisions/004-llm-usage.md:21`, `docs/open-questions.md:28` (row 14)
- ADR 012: model `claude-haiku-4-5`, temperature 0; escalation ladder unchanged; the LLM "emits vocabulary, never coordinates"; alternatives rejected: live LLM on CI, hand-written fake client, self-consistency sampling (multiplies cost/latency xN, "Deferred — revisit if live accuracy degrades"), LLM emitting CBS codes. — `docs/decisions/012-intent-parsing-llm-harness.md:11-13`, `:38`, `:42-47`
- ADR 012 swap conditions: benchmark accuracy below gate -> ADR 004 ladder and re-calibrate; Haiku deprecation -> "swap ID, re-record, re-calibrate (one command each)"; monthly maintenance re-runs `intent:eval` "when anything provider-side changes (model updates land silently)". — `docs/decisions/012-intent-parsing-llm-harness.md:49-55`
- Model escalation is a recorded, measured, unfinished item: swapping Haiku for Sonnet 5 on the finder requires "model+threshold CO-calibration" (confidence distributions differ, correct picks at 0.60-0.88 overlap should-disclose picks), not a one-line change; owner asked twice (2026-07-26) and chose no change; escalating INTENT needs `thinking:'disabled'`, re-calibration of the confidence floor and "a #164 re-record of ~93 fixtures". — `docs/open-questions.md:97` (row #172); `src/answer/intent/client.ts:23-32`; `src/catalog/rerank.ts:24-33`
- Invariants a replacement must preserve (`docs/05-data-rules.md:34-43`): R1 every number traces to a query-result id; R2 the phrasing prompt gets only validated results; R3 numbers in LLM output verbatim, validator blocking; R4 attribution; R5 derived values computed by registered code; R6 chart specs from deterministic code; R7 ranked candidates with confidence, more than one above cutoff or top below threshold -> clarify, never a best guess, with the WP26 third branch (fill a structural axis only if canonical, proven servable, disclosed, correctable); R8 audit record before display, fail-closed, reconstructable from the row alone; R9 semantic binding of direction/comparison claims; R10 units; R11 provisional marking.
- Principle (c) and confidence thresholds: "When data is missing, ambiguous, or stale: refuse or ask for clarification. Never guess." — `CLAUDE.md` principle (c). Current thresholds: intent `answerThreshold 0.9`, `runnerUpThreshold 0.35` (`src/answer/intent/types.ts:407-409`, ADR 012 `:28`); finder confident floor 0.8 (`src/catalog/types.ts:63-73`); fit 0.8 (`src/ingestion/onboarding-fit.ts:41-52`); table parse 0.8, "uncalibrated until the recording run" (`src/answer/table-parse/parse.ts:96-98`). Failure direction is asymmetric by design: a low-confidence correct reading degrades to a clarifying question; a shaky reading is never answered. — `docs/decisions/012-intent-parsing-llm-harness.md:32`
- The confidence today is the LLM's SELF-REPORTED number in its JSON (`confidence: z.number()`, `src/answer/intent/schema.ts:80`), calibrated empirically: correct parses cluster 0.92-0.98 (ADR 012 `:32`), shaky ones 0.75-0.85, and the latest 78-case run has one wrong intent at 0.95 (`benchmark/intent-calibration-report.json`). Lessons: "representability gaps produce HIGH-confidence wrong parses - confidence cannot flag them". — `docs/lessons-learned.md:6349` (2026-07-05 validation-pass entry)
- Defense in depth is explicit: "prompt rules are the primary control, thresholds the backstop, and the deterministic resolver the hard floor." — `docs/decisions/012-intent-parsing-llm-harness.md:32`. And the guard for a degenerate parse "must be the deterministic degenerate-range check, never the model's self-doubt (principle c)". — `src/answer/intent/followup.ts:38-44`
- The reject-only pattern is the codebase's answer to adding a second AI opinion: a role that "may only veto", never approves, sees no raw rows or user question, and whose scope (not verdict) is re-derived by R8. — `docs/decisions/004-llm-usage.md:43`, `src/answer/compose/semantic-check.ts:1-19`, `src/answer/translate/meaning-check.ts:1-11`
- The public claim is "every number traceable to an official CBS cell, with source and date shown", never absolute slogans. — `CLAUDE.md` public-claim rule.

### Inferences
- A model that returns a typed value with a real probability is directly compatible with R7's existing structure (ranked candidates + numeric confidence + threshold -> clarify), and could replace the self-reported `confidence` field, the calibration weak point recorded above; R7's thresholds (0.9/0.35/0.8) were calibrated to Haiku's self-reports and would need re-calibration against any new probability scale (same lesson as #172).
- The reject-only slot (checker/meaning-check style, boolean or class per item) is the lowest-risk insertion point under the repo's own rules: it can only narrow, and it needs no prompt/fixture re-record of the existing chain (ADR 034 pattern, flag-dormant until calibration).
- ADR 004's "ladder" lists embeddings and a bigger model as escalations but not a typed-classification model; adding a new vendor is a new ADR-worthy load-bearing choice (`CLAUDE.md`: "Every load-bearing technical choice gets an ADR ... at least 2 real alternatives").
- GDPR/DPA: sending user question text to a new vendor is a new processor under ADR 004's GDPR seam; a self-hosted or EU-hosted model would be a mitigating factor (ADR 004 alt 3 was rejected on ops and Dutch quality, not on principle).

### Gaps
- ADR 004 says nothing about latency targets per call; the only latency criterion is the ~10 s median in ADR 013.
- The repo does not state the Dutch-language quality bar a replacement must meet other than the labelled sets and benchmark.

## 7. Abstraction seam, feature flags, and the "cheapest mechanism first" rule

### Takeaway
A provider seam exists (`LlmClient`) and is already injected everywhere, but it is string-in/string-out and hash-keyed to Anthropic-style requests; two precedent patterns exist for plugging in a new capability behind a dormant flag (`ENGLISH_ANSWERS_ENABLED`, `SEMANTIC_CHECK_ENABLED`), and one for a separate client interface (websearch). The owner's cheapest-mechanism rule means a new model vendor must be justified by measured evidence, staged as a later conditional phase, and shown to beat the deterministic/no-AI alternative first.

### Cited Findings
- Injection seam: every LLM-calling function takes `client: LlmClient` via `LlmCallOptions {client, model?, maxTokens?}`, extracted "so a field added here reaches every bag by construction". — `src/answer/llm/client.ts:61-73`
- Dormant-flag construction pattern: `semanticCheckOptions()` returns `{}` unless `SEMANTIC_CHECK_ENABLED==='1'` so "no path constructs the client ... zero extra LLM calls or spend exist" while dormant; fail-open/closed via `SEMANTIC_CHECK_FAILMODE`. — `web/lib/turn-options.ts:25-44`
- English path flag: `englishAnswerOptions(lang)` returns `{}` unless `ENGLISH_ANSWERS_ENABLED==='1'` AND the reader is on English; "Dutch pipeline, its prompts and the Dutch benchmark stay byte-identical and English is a separate path"; builds its own SDK instance (`maxRetries:0`, 20 s timeout). — `web/lib/english-answers.ts:16-31`, `web/app/actions.ts:124`, `:685-690`, `CLAUDE.md` (session 131 note)
- Other flags in the same style: `ONBOARDING_ENABLED`, `WEBSEARCH_ENABLED`, `CLARIFY_CLICK_ENABLED`, `ANSWER_FIRST_ENABLED`, `SLOT_PHRASING_ENABLED`, `TABLE_LANE_ENABLED`, `ATTACHMENTS_ENABLED`, `TRIAL_ENABLED`. — `web/app/actions.ts:341-393`, `docs/RUNBOOK.md:88-98`; rollback is "unset + redeploy", flag-off is byte-identical (test-pinned).
- Escalation without code change is anticipated by design: each model is "a single named constant with a recorded escalation ladder ... a one-line change here, triggered only by a measured accuracy miss". — `docs/decisions/025-cbs-catalog-table-discovery.md:30`, `src/catalog/rerank.ts:17-23`
- Owner rule (binding): "Default every new feature to the cheapest viable mechanism first — no AI call, no schema/DB change, no added cost — and escalate only on measured evidence, not speculation ... An LLM-driven or schema-changing version of a feature is a later, conditional phase, built only once usage shows people actually want it." — `CLAUDE.md` Conventions, session 88. Also: ADR per load-bearing choice with >=2 alternatives; module boundaries `answer/`, `query/`, etc. as the split seam (ADR 001); "Provider spend caps ... set" as a Phase 0 gate item (`docs/STATUS.md` checklist).
- Phase-gate rule: "Before adding anything, check docs/03-mvp-scope.md ... Propose it as a roadmap change instead." — `CLAUDE.md` Phase gate.
- Delegation cost-tier rule: cheap tier for mechanical/closed-choice work, top tier for thinking; models named by role in reusable prompts. — `CLAUDE.md` Conventions (2026-07-02)
- Trial seam precedent for a second credential/vendor account: `AnthropicLlmClient(new Anthropic({apiKey: ANTHROPIC_TRIAL_API_KEY}))`, "zero prompt-..." changes, separate capped workspace. — `web/app/trial-actions.ts:9`, `:73`, `docs/RUNBOOK.md:96`

### Inferences
- The lowest-friction plug-in shape, following repo precedent, is a new module + new interface (like `websearch/`, which deliberately did not touch `AnthropicLlmClient`, `src/websearch/client.ts:1-6`) constructed only behind a dormant env flag, first in a reject-only or shadow role (meaning-check/semantic-check pattern) so flag-off stays byte-identical and no existing fixture is orphaned.
- Under the cheapest-mechanism rule, the case for a new vendor is strongest where an existing decision call is measured as slow, costly, or mis-calibrated (the intent call: largest token cost, self-reported confidence, one confident miss; the finder/fit/table-parse chain: co-calibration blocked in #172), and weakest where a deterministic option exists or the call is prose (the prose calls are out of scope for a typed-decision model by construction).
- Because ADR 004's swap clause lists Anthropic as a "default, not a lock-in" and ADR 012 lists a re-record/re-calibrate procedure as the swap cost, a second provider does not need an ADR change to be permitted, but it does need its own ADR for the new vendor, DPA/GDPR handling and calibration procedure.

### Gaps
- There is no existing generic multi-provider abstraction (no provider registry, no routing/fallback between vendors): fallback today is only within the R3/translate ladders (retry then deterministic/Dutch floor), not model-to-model failover. Confirmed by grep: only the Anthropic SDK is a dependency.
- The repo contains no evaluation of any non-Anthropic model.
