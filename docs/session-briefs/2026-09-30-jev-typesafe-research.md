# Jev earns a shadow test, not a switch

**Verdict: do not add Jev to graphmaker.studio now. Run one cheap offline test, then, only if that passes, a dormant shadow-mode pilot on two closed-choice roles.** Jev (TypeSafe AI's "System One" model) answers typed questions (yes/no, pick-one-of-N, score) with probabilities; it writes no text, extracts no slots, and does no arithmetic. Of the product's 16 LLM call roles, 5 are prose and are out of scope by construction, 6 are compound slot objects that Jev cannot emit, and only 3 (table rerank, measure-fit gate, and the `kind` enum inside intent parsing) are plausible candidates, with 2 more (semantic check, English meaning check) as later maybes. The only two motives that survive scrutiny are latency and calibrated refusal, and neither is proven: no Dutch measurement of Jev exists anywhere, independent studies find its probabilities need local recalibration before any threshold is safe, and the product's own per-stage Haiku latency has never been measured, so there is no baseline to beat. Cost is not a motive: a Dutch answer already costs about $0.01. Under the owner's rule (cheapest viable mechanism first, no new vendor on speculation) the correct next step is a repo-only offline eval against the existing labelled Dutch fixture sets, costing cents and touching no user data, and a written go/no-go before any production wiring.

## Jev is a typed classifier with an LLM-style interface

The contract is one hosted call: a `state` (string or JSON) plus a named map of questions. Each question is `noul` (a yes/no probability), `choice` (one of 2 to 255 labels, returning the winner, a probability per label, and a separate `confidence`), or `score` (2 to 10 ordered levels). The official TypeScript SDK's types confirm this shape: `ChoiceResponse {choice, confidence, probabilities}`, `NoulResponse {noul: number}`, `ScoreResponse {score, confidence, legend, probabilities}` ([typesafe-sdk-js types.ts](https://github.com/typesafe-ai/typesafe-sdk-js/blob/main/src/types.ts), GitHub). Options are defined per request in the `criteria` map, so a dynamic candidate list needs no training or registration ([typesafe-sdk-js client.ts](https://github.com/typesafe-ai/typesafe-sdk-js/blob/main/src/client.ts), GitHub). The SDK defaults to `jev-latest`, which means silent model changes unless a version such as `jev-1.13.0` is pinned ([pydantic-ai PR #8740](https://github.com/pydantic/pydantic-ai/pull/8740), GitHub).

Hard limits: about **32k tokens** for state plus the longest question, measured live as 32,878 accepted and the next size refused with HTTP 400 ([genai-prices PR #720](https://github.com/pydantic/genai-prices/pull/720), GitHub); **255 options per choice** ([4esv/jev-eval](https://github.com/4esv/jev-eval), GitHub). Price is quoted as **$0.042 per million input tokens, output free** ([zeke/jev](https://github.com/zeke/jev), GitHub relaying a vendor claim). Independent latency sits at **130 to 420 ms per call**, not the "under 100 ms" of the press release: 275 ms for one question and 310 ms for three ([Spring AI blog](https://spring.io/blog/2026/09/21/spring-ai-typesafe-structured-judgment/), read in full), p50 244 ms and p95 371 ms through Vercel's gateway ([openlayer jevals](https://github.com/openlayer-ai/jevals), GitHub). Accuracy on generic intent routing is level with Haiku-class models and behind frontier models: 84.9% on Banking77, a statistical tie with Claude Haiku 4.5 ([rusanau.me](https://rusanau.me/blog/jev-spring-ai-langchain4j/), snippet). The vendor's "0% hallucination" figure counts schema violations, which are zero by construction; it says nothing about wrong labels ([Layer3 comparison](https://www.layer3labs.io/comparisons/jev-vs-claude-haiku-4-5), snippet). The product's own Anthropic calls already use the API's JSON-schema output mode plus a zod allowlist check at every call site ([client.ts:103-126](https://github.com/Stefan7168/checkdecijfers/blob/main/src/answer/llm/client.ts#L103-L126), repo), so "type safety" is not a gap Jev would close.

## What Jev cannot do here

Jev generates no text at all, so the 5 prose roles and every model-authored caption or note are out ([fdsimms/todo#2781](https://github.com/fdsimms/todo/issues/2781), GitHub). It cannot extract free values: a year, a region name such as "Land van Cuijk", a measure term, or a period phrase like "eerste kwartaal 2024" must still come from Haiku or from deterministic code, because Jev only returns labels drawn from the options you supply ([zeke/jev](https://github.com/zeke/jev), GitHub). TypeSafe's own limitation list, as relayed, says it "cannot perform arithmetic or reliably count" and "struggles with date/time comparisons"; dates are read as text, not as ordered values ([orcarouter summary](https://www.orcarouter.ai/blog/jev-limitations), snippet). That rules out any role that judges a number against a sentence, which is what the semantic check does. The **255-option cap** and the **32k-token cap** mean the full catalogue of tables cannot be one question; the existing keyword recall shortlist of 20 regular plus 4 historic slots ([catalog/recall.ts:44-45](https://github.com/Stefan7168/checkdecijfers/blob/main/src/catalog/recall.ts#L44-L45), repo) fits easily, but anything wider needs rounds, and "probabilities are normalised per call and rounds cannot be concatenated" ([Hindsight PR #4603](https://github.com/vectorize-io/hindsight/pull/4603), GitHub).

Dutch is unproven. TypeSafe says English is the primary language and other languages are handled "not equally well", with no published multilingual evaluation ([docs.typesafe.ai/models](https://docs.typesafe.ai/models), snippet). The closest non-English data point is one Turkish tweet task, where Jev scored 0.813 raw versus 0.693 in English, on one task with n = 1,000 ([betulsimsek/jev-decomposition-tr](https://github.com/betulsimsek/jev-decomposition-tr), GitHub); Turkish is not Dutch and tweets are not CBS table titles. Calibration does not transfer between tasks: the optimal cascade threshold was 0.67 on Banking77 and 0.37 on a 145-class set, and "none of the routing parameters measured on the first held on the second" ([Janus RESEARCH.md](https://github.com/FirasSX914/Janus/blob/main/RESEARCH.md), GitHub). Position bias is real: arithmetic-style accuracy fell from 88% with the correct option listed first to 57.4% with it last, over 11,621 requests, and the first-listed option gains about +0.37 probability on ambiguous questions ([awesome-jev-robustness index](https://github.com/Yifan-Lan/awesome-jev-robustness), GitHub index of studies). Near-synonym candidates are the documented failure: on hard product-query pairs, confidence stayed high while accuracy was about 53%, and 53 rows tied at 0.99 because probabilities are quantised to two decimals ([jev-orderby-bench](https://github.com/yodablocks/jev-orderby-bench/blob/main/README.md), GitHub). CBS table titles that differ by one qualifier are close to that hard case.

## Calibration is the only real prize, and it is not proven

The product's refusal logic already has the shape Jev's output would plug into: ranked candidates with a numeric confidence, an `answerThreshold` of 0.9 and a `runnerUpThreshold` of 0.35, where a low score degrades to a clarifying question and a shaky reading is never answered ([intent/types.ts:407-409](https://github.com/Stefan7168/checkdecijfers/blob/main/src/answer/intent/types.ts#L407-L409), repo). The weak point today is that this confidence is Haiku's self-report, and the repo has recorded that "representability gaps produce HIGH-confidence wrong parses, confidence cannot flag them" ([lessons-learned.md:6353](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/lessons-learned.md#L6353), repo), plus one wrong intent at 0.95 in the latest run. A model trained to emit honest probabilities would be a genuine improvement, if it delivered.

The independent evidence says it does not deliver out of the box. On an out-of-distribution ticket task, pooled expected calibration error was **0.107, 4.4 times the noise floor**; choice questions were overconfident, boolean questions underconfident, and the author concludes that routing thresholds are unsafe without local recalibration ([scienthoon/jev-ood-calibration](https://github.com/scienthoon/jev-ood-calibration), GitHub). Removing the abstain option turned a 95% accurate task into 0% with ECE 0.793; without an "unknown" option the model answered unanswerable items at 0.79 confidence ([jujumilk3/jev-calibration-audit](https://github.com/jujumilk3/jev-calibration-audit/blob/main/FINDINGS.md), GitHub). Probabilities are not internally coherent: P(x) + P(not x) ranged from 0.93 to 1.19 across negation pairs, and identical repeated calls moved by 0.03 to 0.04 ([awesome-jev-robustness index](https://github.com/Yifan-Lan/awesome-jev-robustness), GitHub). A conformal-calibration study reached a 2.65% error rate among auto-routed items, then saw the guarantee break under a shifted taxonomy ([jev-certify report](https://github.com/nikkoxgonzales/jev-certify/blob/main/results/REPORT.md), GitHub). For judge roles, a UPenn preprint reports LLM judges repeat nearly all of Jev's most confident errors, so a cascade gains at most 1.5 points ([arXiv 2609.29769](https://arxiv.org/abs/2609.29769), snippet); Jev is not an independent second opinion. Criteria wording moved paired accuracy from 70% to 96% in one study ([awesome-jev-robustness index](https://github.com/Yifan-Lan/awesome-jev-robustness), GitHub), so every question edit forces recalibration, the same burden ADR 012's "swap ID, re-record, re-calibrate" clause already imposes for Haiku ([ADR 012, revisit triggers](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/decisions/012-intent-parsing-llm-harness.md#L49-L55), repo).

The honest summary: Jev's probability is a usable ranking signal, and with an explicit abstain option and a threshold fitted on the product's own labelled Dutch cases it might beat Haiku's self-report. Nobody has shown that for Dutch, for statistical table metadata, or for this product's question mix.

## Cost and latency reality check

Cost is not a reason to move. The last live benchmark used 47 Haiku calls and 257,279 input tokens for 20 tasks ([live-benchmark-report.json](https://github.com/Stefan7168/checkdecijfers/blob/main/benchmark/live-benchmark-report.json), repo), about 12.9k tokens per task, which at the repo's own price basis of about $1.02 per million Haiku input tokens ([recording-run-plan.md:24](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/session-briefs/2026-10-01-recording-run-plan.md#L24), repo) is roughly **$0.013 per task, consistent with ADR 004's "well under EUR 0.02 per question"** ([ADR 004:32](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/decisions/004-llm-usage.md#L32), repo). A Jev rerank call over 24 candidates with summaries would be on the order of 2k tokens, about $0.0001. Saving a cent per answer is not worth a vendor, an ADR, a DPA and a second calibration regime. A cheaper lever already exists: the intent prompt is about 6.6k tokens and the client sends no `cache_control` ([lessons-learned.md:6234](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/lessons-learned.md#L6234), repo); caching is deferred until spend passes about EUR 50 per month ([ADR 004](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/decisions/004-llm-usage.md#L11-L21), repo), which is right.

Latency is the only measurable motive, and the baseline is missing. The pipeline's whole-answer median is **10,656 ms** (min 7,570, max 19,360) in the September live run ([live-benchmark-report.json](https://github.com/Stefan7168/checkdecijfers/blob/main/benchmark/live-benchmark-report.json), repo), up from 6,465 ms in July. The audit row stores one whole-answer `latency_ms` and per-call tokens, but no per-call time ([audit/types.ts:19-31](https://github.com/Stefan7168/checkdecijfers/blob/main/src/answer/audit/types.ts#L19-L31), repo). The only per-call numbers are for conditional roles: the Haiku meaning check at median 1,392 ms and max 5,135 ms ([meaning-check-eval-report.json](https://github.com/Stefan7168/checkdecijfers/blob/main/benchmark/meaning-check-eval-report.json), repo), and an estimated 0.3 to 0.5 s for the semantic check ([ADR 034:77](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/decisions/034-semantic-fabrication-check.md#L77), repo). Replacing the intent call's `kind` decision with a 300 ms Jev call saves nothing, because slot extraction still needs Haiku. Only the finder path (rerank plus fit, two serial Haiku calls) could shed a whole call, and that path runs inside an async job measured at 88 s end to end ([ADR 027](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/decisions/027-finder-shape-fit-gate.md#L307-L308), repo), where 1 s of model time is noise next to the ingest.

## A shadow-mode pilot that changes nothing a user sees

The pilot follows existing precedents. The semantic check is constructed only when `SEMANTIC_CHECK_ENABLED === '1'`; while dormant "no path constructs the client" and zero extra LLM calls exist ([turn-options.ts:25-44](https://github.com/Stefan7168/checkdecijfers/blob/main/web/lib/turn-options.ts#L25-L44), repo). The English path is a separate client behind `ENGLISH_ANSWERS_ENABLED` with its own SDK instance, `maxRetries: 0` and a hard timeout ([english-answers.ts:16-31](https://github.com/Stefan7168/checkdecijfers/blob/main/web/lib/english-answers.ts#L16-L31), repo). The websearch module sets the third rule: a new capability gets its own interface and never touches `AnthropicLlmClient`, whose request hash keys every recorded fixture ([websearch/client.ts:1-6](https://github.com/Stefan7168/checkdecijfers/blob/main/src/websearch/client.ts#L1-L6), repo).

**Step A, offline only, no deploy.** A script under `scripts/` sends the existing labelled sets to a pinned Jev version: the 10 finder fixtures as one Choice each (candidate ids plus `none`), the 6 measure-fit fixtures as one Choice each (measure codes plus `geen`), and the 78 intent fixtures as one 6-way `kind` Choice plus `unclear`. Run each case three times, the repo's `repeat 3` convention, and once more with candidate order reversed. Record per case: Jev choice, confidence, full probabilities, Haiku's recorded choice and confidence, labelled truth, latency, tokens. Cost is under one dollar. First confirm the fixture questions are project-authored benchmark text with no real user questions; exclude any that are, so Step A needs no DPA. **Step B, shadow in production, only if A passes.** A new client behind `JEV_SHADOW_ENABLED` (unset by default, flag-off byte-identical and test-pinned) runs after Haiku's rerank and fit decisions, never before them, never on the critical path (fire-and-forget, 1,500 ms timeout), and writes one row per decision to a side table: role, Jev version, choice, confidence, agreement with Haiku, latency, error class. No user-visible output changes. Step B needs the DPA and residency questions answered first, because it sends user question text to a new US processor.

Go/no-go, written down before Step A runs. Accuracy against labelled truth must equal Haiku's on every set (11/11, 6/6, and 77/78 or better on `kind`), with zero flips across three repeats. A threshold must exist where every wrong answer sits below it while the auto-answer rate is at least Haiku's under the current 0.9 floor. Expected calibration error after one fitted temperature must be at or below 0.05, and `unclear` or `none` must win on every refusal-category benchmark case. Reversing candidate order may change at most one case per set. Latency from the Vercel region must show p95 under 1,000 ms, and HTTP 429 or 5xx under 1% of calls; rate limits are reported as dynamic and Vercel-gateway users hit free-tier 429s despite paid credits ([Vercel community thread](https://community.vercel.com/t/ai-gateway-typesafe-ai-jev-returns-free-tier-429-despite-paid-credits/49935), snippet). Step B needs at least 200 real shadow decisions per role or four weeks, whichever is later, with Haiku agreement above 95% and every disagreement reviewed by hand. Failing any one line means stop, record the result in open-questions, delete the code.

One measurement precedes all of this: add per-call latency to `LlmCallRecord` and run the live benchmark once, so intent, rerank and fit each have a real number. If the two finder calls together take under 2 s, the latency case for Jev is dead before Step A starts.

## Risks: vendor, calibration, Dutch, data residency

Vendor risk is high. TypeSafe has one product and left stealth on 2026-09-15 on a $40M seed ([Business Wire via Morningstar](https://www.morningstar.com/news/business-wire/20260915525333/typesafe-ai-emerges-from-stealth-with-40m-in-funding-with-new-model-for-composable-ai), snippet). Weights are closed, with no self-hosting and no fine-tuning ([fdsimms/todo#2781](https://github.com/fdsimms/todo/issues/2781), GitHub). No SLA, deprecation policy or roadmap was found in any source, and no named production customer either ([pinggy.io](https://pinggy.io/amp/blog/typesafe_jev_system_one_model_use_cases_vs_llms/), snippet). Rate limits are reported as 1,200 requests per minute, "adjusted dynamically" ([jevaiguide.com](https://jevaiguide.com/jev-rate-limits/), snippet, low trust). Vercel AI Gateway and Cloudflare Workers AI offer a second route ([AnotiaWang/awesome-jev](https://github.com/AnotiaWang/awesome-jev), GitHub, unofficial), which helps availability, not vendor survival. Any adoption must keep Haiku as the fallback and fail toward the existing path or a refusal, never toward a Jev-only answer.

Calibration risk is the core risk, covered above; operationally, a `jev-latest` alias or a silent version bump invalidates every fitted threshold, so ADR 012's pin-and-re-run discipline applies in full, now for two vendors. Dutch risk is unmeasured: the decision prompts are Dutch and the parser emits Dutch place and period names verbatim ([05-data-rules.md:36](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/05-data-rules.md#L36), repo), and no Dutch datapoint for Jev exists anywhere. Data residency: one guide site states that all processing occurs in US data centres with no EU option ([jev101.org](https://jev101.org/guides/jev-privacy-guide), snippet, unverified); the model is reportedly not trained on customer data and zero retention is enterprise-only ([fdsimms/todo#2781](https://github.com/fdsimms/todo/issues/2781), GitHub relaying). ADR 004 already treats user questions flowing to a provider as a GDPR seam needing a DPA and a retention decision ([ADR 004:21](https://github.com/Stefan7168/checkdecijfers/blob/main/docs/decisions/004-llm-usage.md#L21), repo). A second processor needs its own DPA, a transfer basis, a RUNBOOK secrets entry, and by CLAUDE.md its own ADR with at least two real alternatives, which here are "keep Haiku and add per-call latency logging" and "fit a threshold to Haiku's existing confidence, no new vendor". Principle (b), bulk-ingested CBS data, is untouched: Jev would only ever see question text and catalogue metadata, never table cells.

## Action plan

**Thinking.** Stop assuming Jev is faster for this product; the only latency numbers are whole-pipeline, and the calls Jev could replace may be a small share of 10.6 s. Stop treating "typed output" as a benefit; the existing schema mode plus zod allowlists already give it. Accept that accuracy is not on the table, because Haiku is at or near 100% on every measured decision role. Decide that the one thing worth buying is a better-calibrated refusal signal, and decide that this must be shown on Dutch labelled data before any production wiring. Decide now what "pass" means, and write it down before running anything.

**Actions, smallest first.** (1) Add per-call `latencyMs` to `LlmCallRecord` and re-run the live benchmark once; this is a repo-only change with no vendor. (2) Have someone with open network access read docs.typesafe.ai/api, the Jev 1.13 jaggedness page, the pricing page and the data-terms page, and mark each snippet claim in this report confirmed or rejected. (3) Check whether the finder, fit and intent fixture sets contain any real user questions. (4) If the finder path's Haiku calls exceed 2 s and the terms are acceptable, write the Jev ADR draft with the two alternatives and the go/no-go table, and run Step A offline for under one dollar. (5) Only on a full pass, and after a signed DPA, build Step B behind `JEV_SHADOW_ENABLED`, off by default, shadow-only, fire-and-forget, with its own audit rows. (6) After 200 decisions or four weeks, review every disagreement by hand and decide. (7) If any gate fails, record the measured result in open-questions and remove the code.

**Mindset.** Treat this as a measurement project, not an integration project. A two-week-old vendor with no Dutch evidence is not a reason to change a pipeline that passes 14/14, 6/6 and zero fabricated numbers. Every step above is reversible by unsetting a flag or deleting a script. The product's rules already say what to do: cheapest viable mechanism first, refuse or ask when unsure, and never present a guess as settled. That applies to vendor claims as much as to CBS numbers.

## Conclusion

The research changed the question. It began as "where can Jev replace Haiku" and ends as "does graphmaker have a calibration or latency problem that any tool should solve." The repo's own records show the real weak spot is self-reported confidence on confident-but-wrong parses, a property of self-report, not of Haiku. Jev promises a probability that means something, but the evidence says that holds only after local recalibration on the task at hand, which is work the product would have to do with any model. The cheapest experiment is therefore not Jev at all: it is fitting a threshold to Haiku's existing confidence on the labelled Dutch sets and checking whether it separates the wrong-at-0.95 cases. If that fails and per-call latency turns out to matter, Jev is a credible candidate for the two closed-choice finder roles, and the shadow design here is the safe way to find out.
