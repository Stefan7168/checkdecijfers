# ADR 041 — Public embed pages: signed stateless chart URLs, frozen by default, live for Pro

**Status:** accepted, 2026-09-10 (session 93, autonomous — owner away, branch `embed-charts`, not yet merged) — spec Part B as built; design in [superpowers/specs/2026-09-09-story-mode-and-embed-design.md](../superpowers/specs/2026-09-09-story-mode-and-embed-design.md) Part B (session 92, owner-approved in chat).

## Context

Open-questions [#45](../open-questions.md) (chart embedding in third-party sites — owner's initial 2026-07-04 position: a paid feature, two delivery shapes to evaluate), [#46(c)](../open-questions.md) (an exported/embedded view must never silently misrepresent a toggled on-screen state — it must carry the same disclosure a download would), [#49](../open-questions.md)/[#50](../open-questions.md) (live embeds auto-update while downloads freeze; attribution decided per export shape) and [#205](../open-questions.md) (a real Pro/subscription plan, parked as its own future item since 2026-09-06) all predate this build. This ADR builds the mechanism those rows anticipated and updates each of them with how it actually landed (see each row for the as-built note).

Session 92 (2026-09-09, owner present) approved the spec's Part B design in chat: (1) Story mode ships separately (ADR [039](039-chart-presentation-panel.md) addendum) and is out of this ADR's scope; (2) Embed = a pop-up with a code snippet and options, default embed **frozen and served from our own site**, a **Live embed toggle that is Pro-only**; (3) since no Pro plan exists yet (#205), the Live toggle is shown greyed out to everyone except a private, owner-set demo allowlist, so the owner can demo it; (4) "scroll/map" extensions (story inside the embed, a map chart form, homepage/Ontdek embeds) are follow-ups, not built now; (5) Embed is the next build after the session-92 kickoff items. Decision (3) is why open-questions #45's older export-ladder framing ("free watermarked embed with backlink → watermark-free huisstijl embed costs credits") is superseded — see Decision, the ladder, below.

Built session 93 (2026-09-10), autonomous (the owner is away for an extended period; per CLAUDE.md's #118(b) rule this is branch + PR, never a direct push to `main`) — seven implementation tasks plus this docs task on branch `embed-charts`; the SDD ledger and every task's brief/report live under `.superpowers/sdd/2026-09-10-embed/`.

## Decision

**A public chart page is authorized by a signed token, never a database row or a session; it renders through the exact same `ChartView` every other surface uses, so the R1/R6/R11 honesty invariants need no new enforcement; and frozen is the only rendering mode that can ever actually go live today, because the Live path's Pro check has no way to identify the row's owner.**

1. **The token** (`src/chart/embed-token.ts`, pure, no I/O beyond `node:crypto`): `signEmbedToken(auditId, secret)` → `` `{auditId}.{signature}` ``, HMAC-SHA256 over the decimal audit id, signature truncated to 16 bytes, base64url-encoded (22 chars, no padding). `verifyEmbedToken(token, secret)` compares in constant time (`timingSafeEqual`) and never throws — every malformed shape (no dot, non-numeric id, wrong-length signature, wrong secret) returns `null`. No database row per embed: the token itself IS the authorization, the stateless half of the spec's own framing.
2. **The Pro check** (`src/billing/pro.ts`): `hasProPlan({ id, email })` is a plain, owner-set allowlist — `true` iff `email` is non-null and (case-insensitively) listed in the comma-separated `PRO_ACCOUNT_EMAILS` env var. An unset var, or a `null` email, is always `false` (fails closed). This is the #205 seam: every caller (the dialog's `pro` flag, the live route's gate) reads through this one function, so the day a real Pro plan exists, only this function's body changes.
3. **Minting** (`web/app/embed-actions.ts`'s `createEmbedCode`, a `'use server'` action, kept to its own tiny file so `chart.tsx` never drags its audit/db import graph toward the client bundle): requires a session (`currentUserId()`); loads the audit row (`loadAuditRecord`); refuses (`forbidden`) unless the CALLER owns the row, `record.response.kind === 'answer'`, `record.response.chart !== null`, and the row is not retention-redacted (`isRedacted` — see Consequences for this check's triplication across the codebase); on success signs a token and returns `{ token, pro }`, where `pro` is `hasProPlan` evaluated against the CALLER's own session email (`currentUserEmail()`) at mint time. A missing `EMBED_TOKEN_SECRET` returns `unavailable`, never a thrown error.
4. **The dialog** (`web/components/chart-embed-dialog.tsx`: `ChartEmbedButton` + `ChartEmbedDialog`, mounted next to `ChartDownloadMenu`, rendered only when the caller passes an `embed={{ auditId }}` prop): shadcn's `dialog` primitive (Base UI-backed, the session-90 `dropdown-menu` precedent) — tried first, smoke-tested against this project's jsdom/vitest setup, and kept (one local import-path fix, documented at the fix site; no hand-rolled modal was needed). Options: embed language (NL/EN, seeded from the chart's own resolved language), colour (`light`/`dark`/`auto`, → `?theme=`), chart type (`as-shown` passes the current `?form=`, or the spec's own default), and the Live switch — rendered `disabled` with an `aria-describedby` reason whenever the minted `pro` flag is false. The generated code is a plain `<iframe src="{APP_URL}/embed/{token}?...">`. `embed_open`/`embed_copy` count anonymously, riding the SAME `chart_style_usage` counter table WP218 already added (migration 028) rather than a new one; `embed_copy` fires only after a REAL, successful clipboard write, mirroring the existing `default_saved` precedent of counting outcomes, never clicks.
5. **`ChartView` reuse, not a second renderer.** Four new props (`embed`, `embedMode`, `embedFooter`, `initialFormOverride`) join the pre-existing `frameless`. The public route renders the IDENTICAL component every chat/dock/Ontdek/trial chart already uses; `embedMode` strips the interactive chrome (the Weergave tabs, Opmaak/Verhaal triggers, zoom selects, Download, Embed) and substitutes `embedFooter` in their place. Because it is the same renderer, R1/R6/R11 (every digit bound to a spec string; the provisional marker never suppressible) hold automatically — the only new digit-token surface is the one footer date string the ROUTE itself builds (`formatEmbedDate`, the same bare-ISO-slice convention `buildAttributionLine` already uses for this class of timestamp, deliberately NOT the other, locale-flavored date formatter this codebase also has). The whole-card digit-honesty scan is extended to the embed's frozen render, in both languages, by REUSING the house helpers (`scanForUnboundDigits`/`harvestSpecStrings`, copied into `web/app/embed/[token]/page.test.tsx` the same shape `chart.test.tsx` already defines them in) rather than writing a parallel scanner.
6. **The public route** (`web/app/embed/[token]/page.tsx`, `dynamic = 'force-dynamic'`, `metadata.robots = { index: false, follow: false }`): verifies the token, 404s (`notFound()`) on a bad/missing token or a missing audit row, and shows a digit-free "this chart is no longer available" page (both languages, HTTP 200) for a redacted or chart-less record — never an error page. `?form=` is validated with the real `isChartForm` guard before being passed down as `initialFormOverride`, EXCLUDING `'table'` even though `isChartForm` accepts it (final review, Bundle B: table form is never embeddable — the dialog's own Embed button is hidden in table form, so it can never generate a `?form=table` URL, but a hand-crafted one could still have reached this route and rendered it); `ChartView`'s own mount-only effect then re-checks whatever survives against the spec-aware form guards (`lineFormAllowed` etc.) before applying it, so a query string can never force an invalid form. `?theme=` is validated and applied OUTSIDE this file entirely (final review, Fix 2): `web/proxy.ts` turns a validated `?theme=light`/`dark` into an `x-embed-theme` request header (`'auto'`, absent, or invalid sets no header — that option means "follow the reader's own system preference", which needs no override), and `web/app/layout.tsx` reads it and passes it as `<ThemeProvider forcedTheme={...}>` — next-themes' own documented API for forcing a theme regardless of system/stored preference. This replaces an earlier, narrower fix (a per-route `<div className="dark">` wrapper around just the chart) that could only ever flip Tailwind's dark-mode-scoped tokens for markup nested inside it; it could not stop `<ThemeProvider>` itself (mounted unconditionally for every route) from resolving the READER's own OS/browser `prefers-color-scheme` regardless of what `?theme=` said, so `?theme=light` — the embed dialog's own DEFAULT option — silently did nothing on a dark-mode reader, and `?theme=dark` never painted the page's own background (the embed's `frameless` mode clears the card's own background, and the wrapper div painted nothing to replace it). `forcedTheme` drives the SAME `.dark`-class-on-`<html>` mechanism every other page's dark mode already relies on, so both directions — and the page background — are now correct. See [open-questions #226](../open-questions.md), resolved.
7. **The proxy fix — the single most consequential correction of this build, found in Task 5's own review round, not anticipated by the original design.** `web/proxy.ts`'s session-auth allowlist (`PUBLIC_PATH_PREFIXES`) had NO entry for `/embed/`. Every route test exercises `EmbedPage()` directly in jsdom and never goes through the proxy at all, so this gap was invisible to the route's own tests: as first built, EVERY anonymous third-party reader of an embedded chart was being 307-redirected to `/login` instead of seeing the chart — the entire feature was non-functional for the public it exists for, from the moment it would have shipped. Fixed by adding `'/embed/'` to `PUBLIC_PATH_PREFIXES` (a prefix match, deliberately WITH the trailing slash — unlike the exact-match API-route entries above it in the same list, a stray path under this prefix that names no real token just 404s inside the route itself, so there is nothing under it for an accidental sibling route to expose). `isPublicPath` is exported and directly unit-tested (`proxy.test.ts`) precisely because this class of gap — correct route logic, missing allowlist entry — is exactly what a route-level test cannot see; the WP16 go-live's own historical regression (RUNBOOK) was the same shape of bug.
8. **The SiteFooter mechanism — a new, reusable proxy-to-layout signal.** The root layout (`web/app/layout.tsx`) unconditionally rendered `<SiteFooter />` on every route, including `/embed/*`, contradicting the spec's "no site header/footer" requirement for a clean iframe surface. Rather than a second root layout or a Next.js route group (a bigger restructure for one route), `web/proxy.ts` gained `embedRequestHeaders(pathname, searchParams)`: for any `/embed/`-prefixed path it sets a plain request header `x-embed-route: 1`, plus `x-embed-lang` carrying that request's own `?lang=` value — but only once validated by the real `isLang` guard, never trusted raw. `web/app/layout.tsx` reads both via Next's `headers()` API: `x-embed-route` conditionally skips `<SiteFooter />`; `x-embed-lang`, when present, wins over the cookie/`Accept-Language` chain `getLang()` otherwise uses for `<html lang>` (an anonymous third-party reader has no checkdecijfers.nl cookie of their own for that resolution to mean anything). This is the first time this codebase has needed the proxy to hand a route-derived signal down to the root layout, and it is a genuinely reusable pattern for the next route that needs a different shell — not a one-off hack scoped to `/embed/` alone. Proven out already: the final review reused this exact mechanism a third time for `x-embed-theme` (Decision point 6's `forcedTheme` fix), with no change to the pattern itself — only a third key alongside the two above.
9. **Live re-render** (`src/chart/embed-live.ts`): `parseStoredIntent` hand-validates an `AuditRecord`'s stored, untyped `intent` field defensively (the `parseBrandApplied` style already established in `web/app/chart-style-actions.ts` — every field and every discriminated union's `kind` checked explicitly, any shape surprise returns `null`, never a bare cast) before `rerunLive` feeds it to `runQuery(db, intent, { probe: true }) → buildChartSpec`. `{ probe: true }` because a live embed re-render is never a billed/served turn (the same #195 "only a deliverable read counts as demand" discipline `dry-run.ts`'s `echoServability` already follows) — see Consequences for the eviction-GC blind spot this creates. Every failure mode (a malformed stored intent, a thrown error, a refusal outcome) collapses to the same `null`, so the route's fallback-to-frozen logic is one `if (spec === null)` check, never a try/catch it has to reason about itself.
10. **The Pro gate is checked against the row's OWNER, never the anonymous visitor — and it is gated closed by construction, today, for everyone.** `?live=1` only has an effect when `hasProPlan` is true for the audit row's OWNER — a visitor loading a shared embed URL has no bearing on whether Live is honoured; that is a privilege of whoever minted the embed. But `hasProPlan` can only ever match by EMAIL, and the only email-lookup this codebase has is `currentUserEmail()` — the CURRENT session's own JWT claims, useless for looking up an ARBITRARY other user's email on a request rendered days or weeks after that user was ever signed in. No admin/service-role Supabase client exists anywhere in this codebase to build that lookup with (confirmed by a repo-wide search for `auth.admin`/`service_role`/`getUserById` and for a provisioned `SUPABASE_SERVICE_ROLE_KEY` in any env file — none found), and building one is real, unprovisioned scope (a new privileged client, a new secret, RLS-bypassing surface) correctly judged out of bounds for this plan rather than improvised under time pressure. So the route calls `hasProPlan({ id: record.userId ?? '', email: null })` — which, by `hasProPlan`'s own documented fail-closed contract, is `false` for every row, unconditionally. **The practical result: the Live switch in the dialog can show as enabled (computed at MINT time, from the creating user's own session email), and the generated code can carry `live=1`, but the actual render-time re-render can never honour it — it silently and permanently falls back to the frozen render, for every embed, until this lookup is built.** This is not a bug in the code that shipped — every path is tested, safe, and fails closed exactly as designed — but it is the single most important fact about this feature for the owner to understand: **Live is real, shipped, and cannot currently turn on for anyone, regardless of who is marked Pro.** See Consequences and Revisit triggers, and [open-questions #224](../open-questions.md).

**As-built, 2026-09-12 — the lookup is now built (Revisit triggers, below, has the full record).** `src/billing/creator-email.ts`'s `lookupUserEmail` reads `auth.users.email` through the app's existing pg pool; the route now calls it before `hasProPlan`. Live can activate for a real Pro-listed owner **once the owner verifies the pooler role's read access to `auth.users` on the live project** (docs/RUNBOOK.md) — until then this paragraph's "cannot currently turn on for anyone" still holds in practice, but the code path is real, not stubbed.
11. **Framing headers** (`web/next.config.ts`): every route gets `X-Frame-Options: DENY` + `Content-Security-Policy: frame-ancestors 'none'` EXCEPT `/embed/:path+` (note: `:path+`, one-or-more segments — NOT the spec's original `:path*`, zero-or-more), which instead gets `frame-ancestors *` and no `X-Frame-Options` at all. The `:path+` vs `:path*` distinction is load-bearing, not cosmetic: with `:path*` a bare `/embed` (no token) matched BOTH header groups at once, and per the CSP spec a browser ignores `X-Frame-Options` whenever `frame-ancestors` is also present — so that response was, in practice, framable; confirmed live via `curl -sI` before and after the one-character fix. Test-pinned (`next.config.test.ts`) against Next's own path-matcher, not just by inspection. One accepted, harmless quirk remains: Next's header-source matching is case-INSENSITIVE by default while the real `[token]` dynamic route is case-sensitive, so a request to `/EMBED/<anything>` still receives the permissive header even though it can never reach the real embed page (it 307s to `/login`, same generic handling as any other unrecognized path) — closing this structurally would need `experimental.caseSensitiveRoutes: true`, a much broader change than this one route justifies.
12. **`export const revalidate = 3600` — in the spec, deliberately NOT built.** Next's own `dynamic = 'force-dynamic'` (needed regardless, since the token names a different audit row on every request) silently forces `revalidate` to `0` for every fetch on the route (confirmed against the installed Next version's own route-segment-config documentation) — so the spec's hour-long cache would have been a no-op that misleadingly implied caching that never happens, and unsafe if that precedence relationship ever changed: a retention-redacted row must stop rendering on the very next request, on BOTH the frozen and live branches, and an hour-long page cache would risk serving a since-redacted row's content for up to an hour past the sweep. The cost this trades away is re-running the live query on every `?live=1` request rather than at most hourly — accepted, since that query is `{ probe: true }` against our own already-ingested Postgres data, never an external CBS call.

**The export ladder, as built (supersedes open-questions #45's older framing):** free = a frozen embed with attribution and a backlink to checkdecijfers.nl; paid = **Live embed is Pro**, not a credit-priced watermark-free tier. #49 (live auto-updates, downloads freeze) and #50 (attribution decided per export shape) hold as originally resolved; #46(c) is satisfied — the embed footer carries the same disclosure text a download would for the same form/zoom state, and the embed URL itself carries no hide/highlight selection at all to disclose.

## Alternatives considered

1. **A per-embed database row with real revocation** (kill one embed without rotating the secret for every embed at once) — rejected for v1: no schema change is needed for a stateless token, and the spec explicitly chose statelessness. Recorded as a revisit trigger below, not a rejection of the idea itself.
2. **Unsigned, sequential embed ids** — rejected: trivially enumerable, would leak which audit ids exist (and, by extension, roughly how many questions the product has served) to anyone incrementing a URL.
3. **An inline-SVG snippet instead of an iframe** — rejected: loses the live-update path entirely (a pasted SVG is inherently frozen), and CBS attribution/backlink integrity is far easier to guarantee when the server controls the whole rendered surface than when a copy-pasted markup blob can be edited by whoever pasted it.
4. **A separate public-page product** (the Phase-2 shareable-answer-pages idea, open-questions #9) — out of scope: a bigger, differently-shaped feature (an indexable, SEO-facing page) than a third-party-embeddable chart iframe; this route is deliberately `noindex, nofollow` for exactly that reason.

## Consequences

- Zero change to `src/answer/*` or the benchmark; the R1–R11 backend suites are untouched by this build.
- The first dynamic route (`dynamic = 'force-dynamic'`) and the first CSP framing headers this app has ever needed — every other route continues to get blanket `X-Frame-Options: DENY`.
- `chart.tsx` (already large — 2,843 lines) grows by four more embed-shaped props (`embed`, `embedMode`, `embedFooter`, `initialFormOverride`) atop its pre-existing `frameless` — another instance of the file's own growing surface area (ADR 039 already flagged the grid/axis JSX near-duplication as an extraction candidate) rather than a fresh concern this build introduces.
- **`isRedacted` (the retention-sentinel check) now exists as three hand-written, near-identical copies**: `web/app/embed-actions.ts`, `web/app/embed/[token]/page.tsx`, and the pre-existing `scripts/verify-audit-rows.ts`. Each is individually correct and independently tested, but nothing keeps them in sync if the redaction envelope's shape (`src/answer/audit/retention.ts`'s `redactedResponse()`) ever changes — such a change would need all three updated together, with nothing failing loudly if one copy is missed beyond a test on the stale one. Not consolidated in this build because `embed-actions.ts` is a `'use server'` module whose exports cannot be plainly imported into a page component without dragging server-action machinery into it; a shared neutral module (in `src/`, imported by both sides) is the natural fix. Recorded on [open-questions #227](../open-questions.md).
- **The eviction garbage collector cannot see live-embed demand.** `rerunLive`'s `{ probe: true }` deliberately does not bump `cbs_tables.last_queried_at` (the #195 discipline: only a deliverable, served read counts). `src/ingestion/eviction.ts` anchors evictability on `coalesce(last_queried_at, created_at)` — so a CBS table kept alive ONLY by live-embed traffic (no ordinary chat questions against it) looks exactly as stale to the evictor as a table nobody has queried at all, and could be evicted out from under a live embed. After eviction, `rerunLive`'s `runQuery` would return a refusal outcome and the embed would silently and permanently fall back to frozen — no alert, no error, just a chart that quietly stops updating. Currently moot in practice (Live cannot activate at all — Decision point 10), but worth recording now, before it is forgotten, for whenever the Pro-owner-email gate is resolved. Recorded on [open-questions #228](../open-questions.md).
- **Header hygiene — CLOSED in the final review (Bundle A + C).** `embedRequestHeaders` only ever ADDED `x-embed-route`/`x-embed-lang` (now also `x-embed-theme`) to the shared request-headers object; it never explicitly stripped a client-supplied value under those same names first. The risk was previously understated here as only "the layout hiding its own footer... a cosmetic no-op" — that undersold it: `x-embed-lang` also feeds `LangProvider`, so a forged header could override the INTERFACE LANGUAGE on any non-embed route too, not just hide the footer, and `x-embed-theme` (once added) has the identical self-inflicted-only characteristic — it can only ever force the FORGER's OWN page into a theme they didn't ask for via `?theme=`. Still never an auth or data issue (no caller reads any of these three headers for anything security-relevant, and no response is cached keyed on them) — but real trusted-header-injection hygiene worth closing on general principle, and now actually closed: `web/proxy.ts`'s new `applyEmbedRequestHeaders` unconditionally deletes all three keys before conditionally re-setting them, so a forged value can never survive on any path, regardless of what `embedRequestHeaders` itself decides for that request. Recorded on [open-questions #225](../open-questions.md), resolved.
- **`?theme=dark` — RESOLVED in the final review (Fix 2).** The narrow visual limitation this ADR originally recorded (text/border/muted tokens flipped correctly, page background did not) is gone: `?theme=` now drives next-themes' own `forcedTheme` prop at the root layout (Decision point 6), which forces the SAME `.dark`-class-on-`<html>` mechanism every other page's dark mode already relies on — background included. `?theme=light` (the embed dialog's own DEFAULT option) is also fixed in the process: before this change it silently did nothing on a dark-mode reader (the old per-route wrapper never addressed the light case at all, only "dark"), a bug this ADR had not previously recorded. Recorded on [open-questions #226](../open-questions.md), resolved.

## Revisit triggers

- **The Pro-owner-email lookup — this is the one that actually matters.** The moment this codebase gains any way to resolve an arbitrary user id to that user's email (a Supabase admin/service-role client, a mirrored `email` column kept in sync by a trigger, or the real #205 Pro plan bringing its own user-status table keyed some other way), `rerunLive`'s hardcoded `email: null` becomes a real lookup and Live activates for every embed whose owner already qualifies — no other code changes anywhere in this feature. Until then, treat "Live embed" as a demonstrated-but-dormant capability, not a shipped one. [Open-questions #224](../open-questions.md).
  **As-built, 2026-09-12:** resolved. `src/billing/creator-email.ts`'s `lookupUserEmail(db, userId)` reads `auth.users.email` through this app's EXISTING `pg.Pool` connection (`DATABASE_URL` — the same Supabase Postgres project GoTrue's own `auth` schema lives in), chosen over a new admin/service-role client (a new privileged secret) or a mirrored+trigger-synced column (a schema change and a second copy of personal data) — see the design note, docs/session-briefs/2026-09-12-live-embed-creator-lookup-design.md. It validates the id is UUID-shaped before querying and fails closed to `null` on ANY error (no `auth` schema, denied privilege, unknown id), never throwing and never logging the email. `web/app/embed/[token]/page.tsx`'s Live branch now calls it before `hasProPlan`, so Live embeds can actually activate for an owner in `PRO_ACCOUNT_EMAILS` — **once the owner verifies, on the live project, that the pooler role can read `auth.users`** (docs/RUNBOOK.md's new "verify the pooler role can read `auth.users`" step). Until that is confirmed, an unverified/denied read degrades to exactly the prior always-frozen behaviour — nothing breaks either way. The eviction-GC blind spot below is unchanged and now matters in practice the moment that verification passes.
- **Per-embed revocation** — if the owner ever wants to kill ONE embed without rotating `EMBED_TOKEN_SECRET` for every embed at once, that needs a stored, indexed table, not a signature scheme; a bigger change than this build, deliberately deferred (Alternatives, #1).
- **Homepage/Ontdek chart embeds** — those curated specs carry no audit row, so embedding them needs a second token kind (or a different lookup key entirely); not the same code path as this ADR's audit-row-keyed token.
- **Story inside the embed** (`?story=1`) and a map chart form's own Embed button — both named as follow-ups in the spec, neither built.
- **The real #205 Pro plan** replacing `PRO_ACCOUNT_EMAILS` — every caller already reads through `hasProPlan`, so this is a one-function change when it lands, EXCEPT it does not, by itself, resolve the Pro-owner-email lookup gap above: a real plan still needs a way to resolve "this row's owner" to "is that owner's account Pro," which is the same missing plumbing, not automatically solved by the plan existing.
- **The `isRedacted` triplication** (Consequences) — small, contained, worth a future cleanup pass, not urgent. (The header-stripping hygiene gap that used to sit alongside this one was closed in the final review, Bundle A — see Consequences.)
- **The eviction-GC blind spot** — worth the owner's specific attention once Live is ever actually opened up (moot until then, but recorded now so it is not rediscovered from scratch).
