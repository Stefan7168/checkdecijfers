**Status:** accepted and MERGED + LIVE, 2026-09-11 (session 95, autonomous overnight — the owner pre-resolved the decision in [session-briefs/2026-09-10-overnight-visual-upgrade-kickoff.md](../session-briefs/2026-09-10-overnight-visual-upgrade-kickoff.md), decision 2: "retire 'basic Recharts style' as the default look — build the designed default"). Built on branch `visual-designed-default`, PR #10, merged 2026-09-11 (`gh pr view 10`; the "a pull request is open" phrasing above stood stale for several sessions — caught and fixed 2026-09-15, session 103, while adding this file's own chart-card-polish addendum below). Plan: [superpowers/plans/2026-09-11-designed-default-chart.md](../superpowers/plans/2026-09-11-designed-default-chart.md). Spec: [session-briefs/2026-09-10-visual-next-level-plan.md](../session-briefs/2026-09-10-visual-next-level-plan.md) §4.

## Context

Since session 87 (2026-09-07) the default chart was, by owner decision, the look of Recharts' own documentation examples: the `#8884d8` purple / `#82ca9d` green / `#ffc658` yellow palette, a dashed grid in both directions, axis lines on, a dot on every point, 11 px labels, a fixed 256 px height. That decision was executed faithfully (ADR [039](039-chart-presentation-panel.md) pinned it as `STOCK_PRESENTATION`), and it is exactly why the owner said in session 94 that "a graph is just a basic graph, which needs more styling" and asked to lift the chart experience "to the next level" for the product's ICP — freelance journalists and small newsrooms who need a chart that looks publication-ready with no fiddling. The session-94 plan (§4) diagnosed the "basic" look as the pinned literals, not as a rendering shortcoming, and proposed a designed default as a different set of values in the presentation system that already exists. Five of the eight stock colours also fall below the 3:1 warning line on one card (`judgeColor` warns on them), and the stock palette is not colour-blind-safe — a property the owner gave up in session 87 only as a side effect of "use the basic style".

Constraints that bind every option: every number on a chart stays a spec string bound to its cell (R1/R6), the hollow/hatched provisional marker can never be hidden (R11), Recharts' own animation stays off (an export at click time must never capture a half-drawn line — the session-90 refusal), no CSS `aspect-ratio` (the session-92 six-round battle-test lesson), no new library, no schema or prompt change (cheapest mechanism first, CLAUDE.md).

## Decision

The product's stock look is now a **designed default**, built entirely as presentation over the unchanged spec:

1. **`DEFAULT_PALETTE`** = `#0072b2 #d55e00 #009e73 #cc79a7 #b8860b #3a8fc4 #6a5acd #6f8d2a` (`web/lib/chart-presentation.ts`). The first four are Okabe–Ito's blue, vermillion, bluish green and reddish purple — the standard colour-blind-safe set; the other four are hand-tuned to the same luminance band. Measured with the same WCAG formula `judgeColor` uses: every colour is ≥ 3.0:1 against BOTH card colours (`#ffffff`: the weakest is `#cc79a7` at 3.06; `#171717`: the weakest is `#6a5acd` at 3.38), so no default colour ever carries a contrast warning on either theme; the first four stay ≥ 0.07 apart in OKLab under simulated protanopia (min 0.096), deuteranopia (0.076) and tritanopia (0.100), Machado et al. 2009. Both facts are **test-pinned** (`chart-presentation.test.ts` carries the simulation). **One palette for both themes** — no theme hook, and the export (which resolves paint against the light theme, #222) needs no special case. The session-87 palette survives as `RECHARTS_PALETTE` and the old literals as `CLASSIC_PRESENTATION`, both pinned, for the "Classic" look of the template phase.
2. **`STOCK_PRESENTATION`** literals: `markers: 'ends'`, `grid: 'horizontal'`, `axisLines: 'hidden'`, `areaFill: 'gradient'`; line width stays `'normal'` (2 px — the weight comes from the palette and the quiet grid, as in FT/Economist/OWID charts), everything else unchanged. Deep-equal pinned, so the decision cannot drift without an edit.
3. **A new marker mode `'ends'`** (the default): the first and last PLOTTED point of each series plus every provisional point; the rest are drawn at opacity 0 — kept in the DOM exactly like `'provisionalOnly'` already did, so the `[data-point]` count, keyboard walking and click-to-annotate never change. Pure `markerVisible(mode, provisional, periodCode, ends)` returns true for a provisional point in every mode (R11 by construction). Endpoints come from the DISPLAYED (possibly zoomed) spec, so a zoom window's own ends get markers. A marker hidden this way that receives keyboard focus becomes visible (`circle[data-marker="hidden"]:focus-visible { opacity: 1 }` in `globals.css`, test-pinned) — the whole-branch review's a11y finding.
4. **A quiet grid with a hairline baseline.** With `grid: 'horizontal'` the only horizontal lines sit at the two honest labelled values (the plotted min and max already are the explicit `ticks`). With `axisLines: 'hidden'` the category axis still draws a hairline **baseline in the grid colour** as long as any grid is shown (`baselineAxisLine`, exported from `chart.tsx`); grid none + axis lines off is a bare plot. Applied to the category axis of every form (the x axis on line/area/bar, the region y axis on the horizontal bar) and to small multiples; the number axis follows `axisLines` alone.
5. **`areaFill: 'gradient' | 'flat'`** (area form only): a vertical `<linearGradient>` per series, colour at 28 % → 2 %, inside the exported `<svg>`'s `<defs>`; honest because the area form already forces a zero baseline. `'flat'` restores the old 25 % fill; the Style panel offers the toggle in area form only.
6. **Value labels 12 px with a card-coloured halo** (`paint-order: stroke; stroke: var(--card); stroke-width 3`, one shared `VALUE_LABEL_PROPS`), so a label stays legible where it crosses a line or bar. The export inliner resolves `var(--card)` to the light card. Axis ticks stay 11 px muted. Known look: on a frame background WITHOUT the inset card the halo is card-white on the colour — legible, by design.
7. **Height follows width:** `chartHeightForWidth(width) = max(256, min(360, round(width × 9/16)))`, applied as an explicit height from a ResizeObserver (`useElementWidth`, shared with `ChartFrame`) whenever the frame aspect is `'auto'`, small multiples is off and the form is not the table; 256 px until measured (SSR/jsdom unchanged), never CSS `aspect-ratio`. The dock's and the app shell's scroll containers get `scrollbar-gutter: stable` so a classic scrollbar appearing cannot oscillate the width and the height.
8. **Entrance:** tw-animate-css utilities (`animate-in fade-in slide-in-from-bottom-1 duration-300 motion-reduce:animate-none`) on the export CONTAINER — outside the exported `<svg>`, so a download can never capture it; Recharts' own animation stays off.
9. **Header and legend:** the title is `text-base font-semibold`; the unit and the pinned dimensions form one muted line (separate spans); legend entries are chips (`rounded-full border`) with their hide/highlight behaviour and ARIA untouched.
10. **Tooltip crosshair, solid and faint:** `stroke: var(--muted-foreground); strokeWidth 1; strokeOpacity 0.35` on line/area (a muted band on bars). **Deliberately NOT dashed** — the plan proposed a `3 3` dash, which is byte-identical to the curated event-marker `<ReferenceLine>` and close to the dashed story ring; on a touch device (click trigger) the cursor persists after a tap, so a dashed one could be screenshotted as a fake annotation. Superseded plan line noted in the plan file.
11. **Export guard:** the export clone drops `.recharts-tooltip-cursor` AND `.recharts-active-dot` nodes after paint inlining (the active dot is a filled disc with a white ring that would be drawn OVER the hollow provisional marker — a pre-existing R11-in-export gap the new guard closes). A test pins that the paint walk still lines up after the removal.
12. **Gradient presets retuned:** `dawn` ends at `#f9a8d4` (was `#f472b6`), `sand` at `#92400e` (was `#b45309`) — the old `sand` end refused the FIRST default colour, i.e. every chart. A test now gates every preset × every default colour (the session-92 lesson made mechanical).
13. **The Style panel** gained the "Eerste en laatste / First and last" marker option (between "Alle punten" and "Alleen voorlopige") and the area-only "Verloop in het vlak / Gradient fill" toggle; every string has `nl` + `en` entries, no digits.

Surfaces that change by construction (same `ChartView`): the chat, the dock, the five homepage "Ontdek" charts, the anonymous trial, the history view and — once PR #9 merges — the embed's frozen render.

## Alternatives considered

- **Keep "basic Recharts" and only add templates on top.** Rejected: the owner's own words revised the session-87 decision, and a template system on a poor default leaves every untouched chart looking like a code demo — the highest-leverage change is the one every chart gets for free.
- **A light and a dark palette variant** (the plan's §4.2 item 9). Rejected for v1: a single mid-luminance palette that passes ≥ 3:1 on both cards is the cheapest mechanism (no theme hook, no export special case) and it measures clean; a dark variant is a later escalation if real charts on the dark card look muted.
- **A point-count threshold for `'ends'`** (all markers under ~8 points, ends above — the plan's item 3). Rejected: an absolute rule is deterministic and one enum value; a threshold is a second rule to explain in the panel and in the docs. `'all'` is one click away.
- **A series-count-dependent line width** (3 px single, 2 px multi). Rejected as YAGNI — 2 px is the newsroom norm at this width.
- **Rounded bar tops, curve smoothing, Recharts animation.** Not proposed — the recorded refusals stand (a rounded baseline floats the bar off zero; interpolation invents values; an export can capture a half-drawn line).
- **A dashed crosshair** (the plan's own value). Overruled in review — see decision 10.

## Consequences

- Every chart on every surface changes look at once, homepage included — the owner should expect that.
- **A saved account default pins every key it stored.** Anyone who saved a default before this change keeps the classic geometry (grid both, all markers, axis lines) with the new palette and gradient areas underneath, until they press "Standaard" / "Vergeet mijn standaard" — the spec's intended behaviour (§4.3), noted in the RUNBOOK for the go-live.
- Backward compatibility both ways via the per-key sanitiser: an old build reading a stored `markers: 'ends'` drops just that key; the new build reading an old default fills `areaFill` from stock.
- The attachments chart (`UserChartView`, ADR 037) now draws with the new palette (it shares `seriesStyle`/`buildRows`) but keeps its own classic geometry (grid both, axis lines, fixed height). ADR 037 H2 wants a user chart visibly distinct, so this is recorded as a deliberate non-goal, not a defect; a later pass may align it.
- Test pins changed once, deliberately: the `STOCK_PRESENTATION` pin, the palette pins, the phase-0 "stock look" render pins (renamed to the ADR 042 literals), the preset literals, one account-default pin (`grid: 'both'` → `'horizontal'`). No honesty scan changed.
- Residuals recorded, all fail-safe: `useElementWidth` never re-attaches when the ref goes null → element with `enabled` unchanged (a schema-refusal followed by a v1 spec swap on the same mounted instance — unreachable while every stored spec is v1; the chart stays at the 256 px floor); the hook keeps its last width for one frame when re-enabled; `initialDimension`'s 256 still describes the old fixed height (cosmetic).
- Interior points under `'ends'` are invisible but still `cursor: pointer` targets and keyboard-focusable (visible on focus). Acceptable — the tooltip's active dot cues the point on hover.

## Revisit triggers

- Real charts on the dark card look muted → add a dark palette variant (a theme-aware `seriesColor`; the export keeps resolving light).
- The usage counter (migration 028, once applied) shows readers switching markers back to "Alle punten" at a rate worth a threshold → reconsider the point-count rule.
- The owner wants a dashed crosshair after all → it needs its own visual vocabulary distinct from event markers and the story ring, not the `3 3` dash.
- A fifth+ series is common in practice → the palette's colour-blind guarantee only covers the first four; small multiples / the table remain the honest surfaces.

## Session 110 addendum — dimension caption shows labels, not machine keys

The card header's subtitle line (unit + pinned dimensions, this ADR's own decision) rendered each pinned dimension as `${key}: ${label}` — e.g. `Bestedingscategorieen: 000000 Alle bestedingen`, `SoortMutaties: Volume, t.o.v. zelfde periode vorig jaar` — putting the raw CBS dimension KEY (a camelCase machine identifier) in front of every reader on every chart card, homepage included (session 110 UX audit finding #18). Every value on the subtitle line is still a `dimLabels` spec string (R6), so the #254 whole-card digit-scan exemption for this line is unaffected.

## Session 110 addendum — comparison charts with 16-40 series open on horizontal bars

`defaultFormIsTable`/`initialForm`'s blanket rule (>`BAR_LABEL_MAX` (15) series ⇒ Tabel, regardless of `spec.kind` — #229, ADR [041](041-public-embed-pages.md) addendum) was needlessly pessimistic for a many-region COMPARISON: a region-set answer with 16-40 single-point series (e.g. a provincie's ~26 gemeenten — the 12 provincies themselves stay under 15 and were already fine) opened on Tabel, reading as "no chart at all," even though a horizontal bar chart of 16-40 rows is perfectly readable — every label sits on the category axis, and `BAR_LABEL_MAX` already suppresses the on-bar VALUE labels above 15 regardless of form, untouched by this change.

Fixed entirely in `web/lib/chart-view-state.ts`, the single source of truth #229 already established:
- **`isComparisonShaped(spec)`**: a structural test — every series has exactly one point AND there are ≥2 series — never a new field on `ChartSpec`. A time series (even a multi-series `kind: 'bar'` one) is never comparison-shaped; only a single-moment, per-region/category comparison is.
- **`COMPARISON_HBAR_MAX = 40`**: above `BAR_LABEL_MAX` but within this many series, a comparison-shaped, `hbarFormAllowed` spec now defaults to `hbar` instead of `table`. Above 40 (e.g. an "alle gemeenten" ~342-member class), even a horizontal bar stops being a usable chart and Tabel remains the honest default — unchanged.
- **`defaultFormFor(spec)`** is now the canonical function: `spec.series.length > BAR_LABEL_MAX` ⇒ `hbar` when comparison-shaped and within `COMPARISON_HBAR_MAX` and `hbarFormAllowed`, else `table`; otherwise `spec.kind` exactly as before. `defaultFormIsTable(spec)` is now `defaultFormFor(spec) === 'table'` — a thin wrapper, so the Embed dialog's #229 gate (ADR 041) tracks this carve-out automatically with no change of its own. `chart.tsx`'s `initialForm` calc calls `defaultFormFor(spec)` directly (`inStage ? spec.kind : defaultFormFor(spec)`) in place of the old `defaultFormIsTable(spec) ? 'table' : spec.kind` ternary.
- A comparison with ≤15 series is byte-identical to before (`spec.kind`, i.e. vertical bars) — this carve-out only ever changes behaviour strictly above `BAR_LABEL_MAX`.

Tests: `web/lib/chart-view-state.test.ts`'s new `isComparisonShaped` block and the renamed `defaultFormFor / defaultFormIsTable` block (the 15/16/40/41-series boundaries, a 342-series comparison staying Tabel, and — the key non-regression — a 26-series TIME series, i.e. multi-point per series, still defaulting to Tabel: the hbar carve-out never applies outside a genuine comparison shape). `web/components/chart.test.tsx`'s pre-existing 16-series "idea-bank >15 rule" pin was updated to its new, correct expectation (`hbar`, not `table`) with a new sibling pin covering the >`COMPARISON_HBAR_MAX` case, and its region-set describe block (#253) gained a new pin: a 26-series region-set spec now opens on `hbar` BY DEFAULT (no `initialFormOverride` needed), with `scanForUnboundDigits` re-run to confirm the new default form introduces no unbound digit.

**Verification (measured, this addendum only):** `cd web && npm run typecheck` clean. Targeted suites, each run solo with `--maxWorkers=1`: `lib/chart-view-state.test.ts` 66/66, `components/chart.test.tsx` 281/281, `components/chart-embed-dialog.test.tsx` 22/22 (unchanged, confirming no regression) — no full-suite run or `next build` (out of this worktree brief's scope by design; the parent session's own verification block covers those).

## Session 110 pass 3, row 1 addendum — a comparison chart opens on hbar at EVERY series count, not only above BAR_LABEL_MAX

Pass 3 of the session-110 UX audit found the previous addendum's own carve-out still too narrow: a 12-province comparison (well under `BAR_LABEL_MAX`) opened on the vertical `spec.kind` bar by the pre-existing rule, and a vertical bar names no region on its axis — the reader can only tell provinces apart by colour — while its 12 value labels physically overlapped at both 1280×800 and 375×812. The paragraph directly above ("a comparison with ≤15 series is byte-identical to before") is the exact stale framing this fixes and is superseded by this addendum.

**Decision (parent session):** `isComparisonShaped → 'hbar'` now applies at every series count, moved ABOVE the `> BAR_LABEL_MAX` gate in `defaultFormFor` — a horizontal bar is the only form that puts the region on an axis, so it is strictly better than a vertical bar for a comparison shape regardless of how few series there are. `hbarFormAllowed(spec)` still gates it (a comparison-shaped spec whose `kind` is not `'bar'` — never actually produced today — still falls through to the pre-existing rule). `COMPARISON_HBAR_MAX` (40) is unchanged as the upper bound above which even a horizontal bar stops being usable and Tabel remains the default. A spec that is NOT comparison-shaped (any genuine time series, single- or multi-series) is completely untouched — it keeps exactly the old rule (Tabel above `BAR_LABEL_MAX`, else `spec.kind`).

```
export function defaultFormFor(spec): ChartForm {
  if (isComparisonShaped(spec) && hbarFormAllowed(spec)) {
    return spec.series.length <= COMPARISON_HBAR_MAX ? 'hbar' : 'table';
  }
  if (spec.series.length > BAR_LABEL_MAX) return 'table';
  return spec.kind;
}
```

**Existing charts affected:** none of `ONTDEK_CHARTS`/`GALLERY_STORIES` (`backend/chart/curated.ts`) are comparison-shaped — every curated homepage/gallery card is a single-canonical-measure time series (one or two series, each with `windowLength` > 1 point), so this change is invisible on the public gallery and landing page. The only surfaces that actually change form are live chat/dock/history answers whose spec is genuinely comparison-shaped at ≤15 series (the region-set answer class this row's repro used, e.g. `!!regionset provincies`'s 12 provinces) — those now open on Liggend instead of Staaf by default; a viewer can still switch back to Staaf manually.

**Tests:** `web/lib/chart-view-state.test.ts`'s `defaultFormFor / defaultFormIsTable` block gained a 2/12/15-series comparison pin (all `hbar`, replacing the old "at or below `BAR_LABEL_MAX`: `spec.kind`" pin, which is now split into a single-series-only case). `web/components/chart.test.tsx`: three tests whose fixtures (`multiRegionBarSpec`, a hand-built 2-series comparison) are comparison-shaped and previously relied on their FRESH-mount default being the vertical Staaf form now select Staaf explicitly before asserting on it (the ADR 042 hairline-baseline pin, the chart-card-polish grid pin, the S3 arrow-key-order pin, and the comparison-story-highlight pin) — none of these tests were about the default form itself, so this is a fixture-setup fix, not a behaviour change to what they verify. One gap surfaced in the process — closed same session (hbar highlight parity): `RegionBar`'s `fillOpacity` was always correctly wired to `payload.dimmed` (the visual effect was never actually missing), but — same as the pre-existing `SeriesBar`/Staaf gap its own doc comment already named and fixed — a custom Recharts `shape` fully replaces the library's own rendering, so the `data-series-dimmed` marker itself was not forwarded onto the drawn `<rect>`, meaning any marker-based assertion (rather than one on `fill-opacity` directly, as the pre-existing "Liggend" tests happened to use) would have wrongly read hbar as having no dim behaviour at all. Fixed by forwarding `data-series-dimmed={dimmed ? 'true' : undefined}` on `RegionBar`'s rect, mirroring `SeriesBar`'s existing pattern exactly (same 0.25/1 opacity values, no new number introduced). See `web/components/chart.tsx`'s `RegionBar` and the new/updated pins in `web/components/chart.test.tsx`'s hbar and comparison-story-highlight tests.

## Session 110 pass 3, row 3 addendum — the hbar chart's height now grows with its own series count

Row 1's carve-out (above) made the horizontal bar the default at every comparison series count, but the chart's height (ADR 042 decision 7, `chartHeightForWidth`) only ever followed the CARD'S WIDTH — a fixed row pitch that shrinks as more regions are added. At 26 gemeenten the audit measured an 8.1 px row pitch against 13 px of label text: every adjacent category label collided, at both the 1280 and 375 px viewports (session 110 UX audit pass 3, row 3).

**Fix, `web/lib/chart-view-state.ts`:** `HBAR_ROW_PX = 20` (a comfortable margin over 13 px label text) and `hbarChartHeight(seriesCount, baseHeightPx) = max(baseHeightPx, min(seriesCount * HBAR_ROW_PX, HBAR_MAX_HEIGHT_PX))`, where `HBAR_MAX_HEIGHT_PX = HBAR_ROW_PX * COMPARISON_HBAR_MAX` (800px) — the same upper bound row 1 already uses to decide whether hbar is offered at all, enforced independently here because an explicit `initialFormOverride="hbar"` (the embed route's escape hatch) can still hand hbar a spec with more series than that. `baseHeightPx` is whatever the EXISTING width-based rule already produced — this function only ever grows it, never shrinks it, so a comparison with few regions (e.g. the 12-province chart row 1 fixed) is completely unaffected: `hbarChartHeight(12, 360) === 360`.

**Wiring, `web/components/chart.tsx`:** the previous single `autoHeightPx` calc is now `widthHeightPx` (the old width-only rule, byte-identical) feeding a new `autoHeightPx` that applies `hbarChartHeight` only when `activeForm === 'hbar'`, using the unmeasured 256px floor (`CHART_MIN_HEIGHT_PX`) as the base BEFORE the first `ResizeObserver` callback lands too — a many-region hbar chart never flashes a cramped default height even for one paint. Every other form (`bar`/`line`/`area`) passes `widthHeightPx` straight through, completely unchanged. Because `autoHeightPx` is now always non-null for hbar, the hbar form always sets an explicit inline height (never falls back to the `h-64` CSS class) — a behaviour-invisible implementation detail (256px via class vs. 256px via inline style look identical) that only matters for a test asserting on `className` vs `style.height`, none of which existed for hbar before this row. **Embed mode:** `autoHeightPx` (already row-boosted) is what `embedHeightValue` wraps in its `min(…, 100dvh - …)` frame-relative CSS — the row minimum and the frame-relative rule compose automatically, with no separate embed-specific code path.

## Session 110 pass 3, row 10 addendum — an hbar chart above BAR_LABEL_MAX always labels its first and last row

Row 1's carve-out made a comparison chart open on the horizontal bar form at every series count, and row 3's addendum gave it a row-proportional height — but a 16-40-series comparison (above `BAR_LABEL_MAX` (15), the pre-existing value-label thinning threshold) combined that thinning with the hbar number axis's own "no invented ticks" design (`<XAxis tick={false}>`, decision-time honesty rule: the axis draws no ticks because a tick position implies a value nothing on screen actually measured) to leave the chart with **zero numbers anywhere** — the 26-gemeente chart the session-110 audit's own repro used has no digit on it at all; every value exists only in the proof panel, the Tabel view and the CSV (pass 3 row 10).

**Decision (parent session):** keep both rules exactly as they are — no invented ticks, and the >`BAR_LABEL_MAX` thinning of per-bar labels — but **always label the extremes**: on an hbar chart with more than `BAR_LABEL_MAX` plotted rows, the FIRST and the LAST plotted row (in the spec's own order, R6: never re-sorted here) carry their real `formattedValue` label; every row in between stays unlabelled. When a ranking record sorted the series (ADR 054's `deriveRegionRanking`), those two rows are the ranking's top and bottom member; when the series arrived unsorted, they are simply the spec's first and last rows. The vertical bar form (`SeriesBar`/`valueLabelPlan`'s `barLabels`) keeps its own unchanged all-or-nothing rule: its labels sit ABOVE each bar and collide horizontally as bars narrow, while an hbar row has the chart's full width to itself, so two lone extreme labels can never collide with the unlabelled rows between them — this is a genuine hbar-only affordance, not something the vertical form could adopt for free.

**Fix, `web/components/chart.tsx`:** a new `HbarLabelMode = 'all' | 'extremesOnly' | 'none'` replaces the old boolean `hbarLabelsShown`. `hbarLabelMode` is `'none'` when nothing is plotted, `'all'` at or below `BAR_LABEL_MAX` (the pre-existing rule, byte-identical), and `'extremesOnly'` above it. `hbarExtremeKeys` is computed once, over `regionChartRowsAll` (every region in the spec, matching the existing `hbarPlottedCount` scope) — the same "counted over every region, not just the visible ones" discipline the thinning rule already used, so hiding a region can never change which rows are the labelled extremes. `RegionBar` (the hbar shape function) now takes `labelMode` and `extremeKeys` in place of the old `showLabels` boolean, and decides per row: `'all'` labels every plotted row, `'extremesOnly'` labels only a row whose own `key` is in `extremeKeys`, `'none'` labels nothing — the same `data-role="bar-label"`/`data-label-for` binding as before, so R1/R6 traceability is unaffected; only WHICH rows get a `<text>` element changed. `rightMarginForLabels` (the space reserved for the value-label column) now checks `hbarLabelMode !== 'none'` instead of the old boolean, so the two extreme labels in `extremesOnly` mode still get the margin they need.

**Tests, `web/components/chart.test.tsx`:** a new `'ChartView — #253/row 10 hbar extreme-only value labels above BAR_LABEL_MAX'` describe block pins the two boundary cases the decision names explicitly: a 26-row hbar (`regionSetBarSpec(26)`) renders exactly two `data-role="bar-label"` elements, bound to the first and last series' own `resultId`s and matching their own `formattedValue` strings (`scanForUnboundDigits` confirms no other digit escaped), and a 12-row hbar (at or below `BAR_LABEL_MAX`) still labels every row — the pre-existing rule, unchanged.

## Session 110 pass 3, row 11 addendum — a comparison-shaped chart uses one palette colour for every series

`seriesColor` cycled the 8-colour `DEFAULT_PALETTE` by series index unconditionally, so a comparison-shaped chart (every series one point, >= 2 series — `isComparisonShaped`, chart-view-state.ts) repeated colours past the 8th series: the session-110 audit's own 12-province repro had Zuid-Holland/Groningen both `#0072b2`, Noord-Holland/Drenthe both `#d55e00`, and so on (pass 3 row 11) — and on the default vertical-bar form (row 1, before it defaulted to hbar) colour was the ONLY thing telling two bars apart. The palette was chosen (decision 3) as a colour-blind-safe way to distinguish several genuinely different SERIES on one axis (a time series' several regions/measures over the same periods); a comparison's series are not distinguished by colour at all in the reader's mental model — the region name on the category axis already does that job, and the measure being plotted is the same for every bar. Colour there was never carrying information, it was just running out of distinct values to show.

**Decision (parent session):** a comparison-shaped chart uses the palette's FIRST colour for every un-overridden series; an explicit per-series `seriesColors` override (the Style panel) still wins regardless of shape. A genuine time series — any line/area chart, or a multi-point `kind: 'bar'` one — is never comparison-shaped and keeps the existing per-series cycling palette unchanged.

**Fix, `web/lib/chart-presentation.ts`:** `seriesColor(values, index, paletteIndex = index)` gains an optional third parameter. The override lookup stays on `index` (the series' own identity — an override always wins on the exact series it names); only the PALETTE FALLBACK now reads `paletteIndex`, defaulting to `index` so every pre-existing call site (`chart-small-multiples.tsx`, `chart-template-thumb.tsx`, `chart-stage.ts`'s `atmosphereState`) is byte-identical with no change of its own.

**Wiring, `web/components/chart.tsx`:** `colorFor` (the one function `buildRows` and `buildRegionRows` both share, feeding every legend swatch, tooltip swatch, hatch pattern and now the hbar row colour too) computes `comparisonPalette = isComparisonShaped(displaySpec)` once and passes `paletteIndex: comparisonPalette ? 0 : i`. Because `buildRegionRows`/`RegionBar` and `buildRows`/`SeriesBar`/the legend all read the SAME `colorFor`, this one change makes every surface — the hbar chart, a vertical-bar fallback, the legend swatches, the tooltip swatches — agree on the single shared colour with no separate legend-specific code: the legend's swatches become one colour for a comparison automatically, and its hide/highlight buttons are completely untouched (they never depended on distinct colours to function).

**Tests:** `web/lib/chart-presentation.test.ts` pins `seriesColor`'s new parameter directly (`paletteIndex` picks the palette slot independent of the series index; an override on `index` still wins over `paletteIndex`). `web/components/chart.test.tsx`'s new `'ChartView — #253/row 11 single palette colour for a comparison-shaped chart'` describe block pins: a 12-series region comparison renders every bar with the same fill (`DEFAULT_PALETTE[0]`); a 3-series multi-point time series (never comparison-shaped) keeps 3 distinct palette colours; an explicit `seriesColors` override on a comparison-shaped chart still wins on the overridden series while the other two fall back to the shared colour.

## Session 110 pass 4, row 14 addendum — end-of-line labels drop a redundant shared period prefix

Every end-of-line label on a comparison-shaped multi-region time series repeated the same period — the flagship 6-region chart (ADR 055) showed six copies of `2024: ` — eating most of the right margin row 2's own addendum (above) had just started sizing off the container's real width. When the plotted series end on the same period, that period is redundant six times over: the x-axis already states it once. But a series that ends on an EARLIER period than the others (Eemsdelta's partial-coverage case, ADR 055) is exactly the situation where the prefix is load-bearing — that label is the only thing on screen saying which period ITS number is for.

**Decision (parent session):** `valueLabelPlan`'s `endLabels` (`web/components/chart.tsx`) omit the `"period: "` prefix from every end-of-line label's `text` **only when two or more series have a last plotted point, and every one of them shares the same `periodCode`**. A single-series chart is unaffected (its one end label still states its period, unchanged from before this row); any series ending on a different period leaves EVERY label in that chart prefixed, never just the differing one — a mix of prefixed and bare labels on the same chart would itself read as inconsistent, so the self-describing case wins for the whole chart, matching ADR 055's own MS1 per-series honesty framing.

**The tick-less fallback.** The period being "redundant" assumes the x-axis is actually showing it. Row 2's own measurement found a real case where it doesn't: a narrow container can leave the x-axis with **zero rendered ticks** (Recharts drops ticks it cannot fit without overlap). Dropping every label's period in that situation would state the period nowhere at all — a real honesty gap, not just clutter. `EndLabelsOverlay` now also calls Recharts' `useXAxisTicks()` — the axis's own POST-collision rendered tick list, not a width estimate of our own — and when it comes back empty, reinstates the prefix on exactly the topmost label after its own y-collision pass (`placed[0]`, session-110 pass-4 row 3's stacking order), so the period still appears once on screen. `EndLabelSpec` carries a `periodOmitted` boolean (mirrored from `valueLabelPlan`'s own "all last points share one period" check, never re-derived from parsing the label text) so the overlay knows which labels are eligible for this reinstatement.

**Right margin.** `rightMarginForEndLabels` (row 2's own fix) is computed from `plan.endLabels`' own `text` field, so the shorter, prefix-less text shrinks the reservation automatically — no separate change needed. The one known, accepted limitation: the tick-less fallback's reinstated prefix on `placed[0]` is decided AFTER the margin was already sized from the (shorter) bare text, so in the narrow double-edge case where the axis is simultaneously tick-less AND the margin is at its tightest, that one label's text could in principle be wider than the space reserved for it. This never drops or truncates a digit (R1/R6 — the label is still the complete spec string, just possibly closer to the card edge than ideal), so it is a cosmetic residual, not a data-honesty regression, and is left for a future pass if it is ever observed in practice.

**Tests, `web/components/chart.test.tsx`:** `valueLabelPlan` pinned directly — a 3-series spec all ending `2024JJ00` produces bare `text` (`'1,0'`, `'2,0'`, `'3,0'`) with every `resultId` still individually bound (R1); a 3-series spec where one series (Eemsdelta-style) ends `2023JJ00` instead keeps every label prefixed (`'2024: 1,0'`, `'2024: 2,0'`, `'2023: 3,0'`). The pre-existing row 3 collision test (two series both ending 2024, near-adjacent values) was updated for the new expected wording: with a real x-axis tick list present (the common case), both end labels come back bare and un-truncated.

**Verification (measured, this row only):** `cd web && npm run typecheck` clean. `components/chart.test.tsx` 308/308, solo, `--maxWorkers=1` (three runs in this worktree session: the first surfaced the row 3 test's now-stale expectation, the second caught that jsdom's `useXAxisTicks()` returns a real (non-empty) tick list rather than `undefined` in this fixture — so the tick-less fallback path itself is exercised only by code inspection here, not a dedicated render test; a future session adding a partial `recharts` mock for `useXAxisTicks` could close that gap — the third run is the green one reported above).
